# 다음 구현 단계와 진행 기록

기준일: 2026-09-19 · 시작 커밋: a48987a · 제품 상태: **제한된 시험판**

## 시작 상황

기본 기능(P1~P3)과 시험판 배포(P4)는 이미 존재했습니다. 기존 보고서의 자동시험은 41개 통과였으나, 일반 출시 필수 수용시험 54개는 통과 8개·차단 2개·미실행 44개였습니다. 환경별 시험 4개도 미실행이었습니다. 원래 00/01/02 문서는 요구사항 기준이므로 보존합니다. 이 문서가 후속 진행 순서를 설명하고, 실제 결과는 검증 보고서와 증거 파일에 연결합니다.

## 이번 작업의 상황·결정·설명

### 창 전환이 막힌 P0 시험

- 상황: 이전 Excel 반복 실행기는 Windows의 전면 전환 거부로 제품 캡처를 한 번도 호출하지 못했습니다. 오대상 0건은 정확도 통과가 아니었습니다.
- 결정: 시험용 단축키로 사람이 선택한 foreground를 캡처하고, 실행 전에 고정한 JSON 계획과 비교하는 수동 세션 도구를 추가합니다. 창 전환 권한이나 비공개 Explorer 메시지에 의존하지 않습니다.
- 근거: 시험이 확인해야 하는 것은 실제 사용자가 선택한 대상의 정확도입니다. 전면 전환을 강제하는 능력이 아닙니다. 기대값을 실제 응답에서 만들어 쓰면 잘못된 결과도 정답이 되므로 기대값은 사전에 정합니다.
- 결과와 제한: 구현 및 자동 검증 결과는 아래 최종 기록에 기입합니다. 50회·창/탭/프로세스 조건을 갖추지 못한 작은 표본은 전체 Gate가 아닙니다.

### 단축키 직후 선택 변경

- 상황: HWND·포커스·뷰가 그대로여도 Excel 셀이나 탐색기 선택은 바뀔 수 있었습니다. worker가 시작되기 전에 바뀐 위치를 두 번 읽으면 정상 캡처로 승인될 수 있었습니다.
- 결정: foreground 스냅샷 전에 새 입력 감시를 시작하고, 응답을 승인하기 전 새 키/버튼/휠 입력이 있으면 저장하지 않습니다. 시작 단축키의 키 해제는 무시합니다.
- 근거: 정확히 어느 위치를 의도했는지 알 수 없으면 다시 누르도록 안내하는 편이 엉뚱한 위치를 남기는 것보다 낫습니다.
- 저장 경계: 검증된 응답을 승인하면 감시를 종료하고 확정된 DTO를 DB에 저장합니다. 디스크 쓰기를 기다리는 동안 사용자가 다음 작업을 시작했다고 이미 읽은 위치를 취소하지 않습니다.
- 검증의 범위: 실제 ApplicationContext와 지연 응답/저장소를 사용하되 입력 콜백은 합성 주입합니다. 실제 Excel 입력 시험과 구분합니다.

### 선택한 ZIP의 종류

- 상황: Shell은 ZIP을 탐색 가능한 폴더로도 표시합니다. 기존 구현은 그 속성을 그대로 DB 종류로 써서 실제 파일을 폴더로 남길 수 있었습니다.
- 결정: 선택 항목은 실제 파일시스템 속성으로 파일/디렉터리를 구분하고, 바로가기는 파일로 유지합니다. ZIP 내부 가상 화면의 기존 지원 제외는 유지됩니다.
- 근거: 사용자가 고른 ZIP 파일은 파일 책갈피여야 하며, 미허용 확장자 정책에 따라 파일 위치를 표시해야 합니다.
- 공식 근거: [Microsoft의 Shell 폴더와 파일시스템 구분 설명](https://devblogs.microsoft.com/oldnewthing/20171101-00/?p=97325). 실제 ZIP 속성과 제품 분류를 함께 확인하는 시험을 추가합니다.

### 파일 위치 표시 직전의 사용자 이탈

- 상황: 기존 코드는 이탈 여부를 검사한 다음 Shell 경로 2개를 해석했고, 그 해석이 지연되는 동안 생긴 새 입력을 다시 확인하지 않았습니다.
- 결정: 두 경로 해석이 끝난 직후, 실제 위치 표시 API 호출 전에 사용자 이탈과 전체 기한을 다시 확인합니다. 중단 시 임시 PIDL은 모두 해제합니다.
- 근거: 사용자가 기다리다 다른 일을 시작했다면 뒤늦게 새 창을 요청하지 않아야 합니다. 이미 보낸 외부 동작을 취소할 수 있다는 뜻은 아닙니다.
- 공식 근거: [SHParseDisplayName 문서](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shparsedisplayname)는 이 호출이 UI를 멈추게 할 수 있어 백그라운드에서 실행하도록 안내합니다.

### 시험 판정과 성능 수치

- 상황: 기존 반복 실행기의 JSON은 파일 해시나 실행 오류를 통과 판정에 모두 반영하지 않았고, 창 활성화 실패 시간도 p95 표본으로 섞었습니다.
- 결정: 파일 해시를 읽지 못하거나 변경되거나 실행 오류가 있으면 성공 판정을 내리지 않습니다. 50회 미만은 작은 표본으로 표시하고, 성공한 worker 호출의 시간만 별도로 계산합니다.
- 근거: 실패한 준비 동작의 시간은 캡처 성능이 아닙니다. DB 커밋을 측정하지 않은 값은 제품의 캡처→커밋 성능으로 설명하지 않습니다.

### 로컬 실행 환경

- 상황: 기본 exec 도구는 프로세스를 만들 때 Windows 접근 거부 오류가 났습니다. Node 실행 경로는 동작했지만 처음에는 Windows 환경 변수가 빠진 빌드 서버가 재사용되어 NuGet path1 오류가 발생했습니다.
- 결정: 로컬 Node child_process로 저장소 SDK를 실행하고, 해당 자식 프로세스에만 Windows/.NET 경로를 제공하여 새 MSBuild 프로세스로 locked restore를 수행했습니다. 시스템 설정이나 SDK는 바꾸지 않았습니다.
- 확인: 새 프로세스 locked restore가 통과했습니다. 초기 실패도 evidence/continuation-2026-09-19에 보존합니다. IPC 실행기를 dotnet DLL 방식으로 실행했을 때 자기 실행 경로가 dotnet.exe로 잡혀 프레임 오류가 발생했습니다. 동일 코드를 EXE(apphost)로 실행하여 12/12 통과를 확인했고, 잘못된 실행 방식의 실패 로그도 구분해 남겼습니다.

## 완료 결과

- Locked restore 및 전체 Release 빌드 통과: 경고 0, 오류 0.
- 자동검증 84개 통과: Core/Storage 13, IPC 12, Desktop 22, Windows adapter 10, ExcelSeries 판정 13, CaptureSession 판정 14. 상세 증거는 [검증 보고서](validation-report.md)의 후속 섹션에 연결했습니다.
- 실제 ZIP의 Shell 폴더 속성을 재현한 뒤 파일로 분류하는 것을 확인했습니다. 사용자 이탈·입력 경쟁은 실제 앱 흐름과 합성 콜백/지연을 조합한 시험이며 실제 Office 전체 조작을 대신하지 않습니다.
- self-contained win-x64를 artifacts/publish/continuation-20260919에 생성했습니다. SDK 경로 없이 실행한 worker가 잘못된 입력을 정상 거절했습니다. [파일 해시](evidence/continuation-2026-09-19/build-manifest.json).
- PowerShell 내부의 외부 EXE 실행 문제로 build.ps1 전체 실행은 차단으로 남겼습니다. 그 안의 SDK 빌드·시험을 직접 실행한 결과와 구분했습니다.
- 사람이 창/탭을 선택하는 실제 P0-A/B 50회는 이번 도구 세션에서 수행하지 않았습니다. 자동 실행 도구의 전면 전환 제한을 우회하거나 제품의 시험판 표기를 올리지 않았습니다. 다음 실행에는 [시험 도구 안내](../tools/WindowsChecks/README.md)와 [표본 기대값 계획](../testdata/p0-capture-plan.sample.json)을 사용합니다.
- 원래 명세, 이전 증거, 기존 배포 디렉터리를 보존했으며 원격 게시나 커밋은 수행하지 않았습니다.

## 다음 실제 실행에서 남겨야 할 것

1. 합성 fixture 계획을 확정하고 P0-A/P0-B의 실제 50회 결과, 잘못된 대상 수, 안정 상태 실패를 기록합니다.
2. 첫 캡처 3초 timeout은 원인이 아직 확정되지 않았습니다. 첫 호출과 후속 호출의 worker 시간을 분리해서 수집한 뒤 제한시간 변경 여부를 판단합니다. 이번 작업만으로 제한시간을 늘리지 않습니다.
3. U03/U09/P0-D와 예외 시험은 실제 입력·Office 동작을 관찰하고, 지원 중인 Windows 및 업무 정책 환경은 별도 호환성표에 기록합니다.
4. 50회 DB 커밋 p95, 1,000개 실제 목록 표시 p95, 100회 연동/장시간 자원 측정을 마친 뒤 정식 출시 여부를 판단합니다.
